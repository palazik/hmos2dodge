# OP13 graphics components

The supplied HarmonyOS vendor already contains a native OHOS Mesa stack.
It does not require copying Android's Bionic EGL libraries into HarmonyOS.
The adapted allocator/composer use DRM buffers; Mesa's OHOS native-window
and buffer-sharing paths still require separate verification on OP13.

`bash port/scripts/test_egl.sh` extracts only the three required Mesa
libraries from the original donor and runs an ARM64 OHOS program under
QEMU user mode. The isolated namespace has no host DRM, KGSL, disks or
network. The test dynamically loads EGL/GLES, creates a surfaceless EGL
1.5 pbuffer context, clears and reads back a red pixel, compiles and links
vertex/fragment shaders, draws a triangle and reads back green. Both pixel
checks passed with Mesa softpipe. Library hashes and limits are recorded
in `egl-smoke-result.json`. This is a userspace rendering test, not DSU
emulation, OP13 scanout, GPU acceleration or SceneBoard execution.

## Stock graphics payload

`prepare_op13_modules.py` stages the audited 109-module dependency closure.
It also verifies the approved stock vendor image against its payload
extraction record and extracts only these four files:

- gen80000_aqe.fw
- gen80000_gmu.bin
- gen80000_sqe.fw
- gen80000_zap.mbn

These filenames occur in both the OP13 capture and KGSL driver. The actual
bytes come from `op13_stock/vendor.img`, extracted from the user-approved
stock payload. They are kept in `out/modules/op13-current/firmware`, with
per-file hashes and source-image provenance. No firmware partition is
written, no firmware is loaded, and OEM trust/firmware compatibility on
the device has not been established. Module firmware-name annotations
are incomplete; their absence does not prove no additional firmware is
needed by the dependency set.

The supplied vendor_boot early `modules.load` lists 153 names. Of the
109 selected graphics dependencies, 54 are absent, including msm_drm and
msm_kgsl. The module bytes and dependencies are available; their actual
loading still needs integration. Neither this list nor the Android capture
proves modules will be resident at the DSU handoff.

## Isolated service configuration

```sh
python3 port/scripts/prepare_op13_modules.py \
  --early-modules work/module-sources/ba81b50a633cfc4b
python3 port/scripts/prepare_native_framework.py --graphics
python3 port/scripts/test_framework.py --staged
```

The separate `out/framework/graphics` component retains the eight framework
services and adds allocator_host, composer_host, render_service and
multimodalinput. Their donor executable arguments, credentials, capabilities,
tokens, sockets and SELinux domains are preserved. Composer and allocator
keep HDF host IDs 7/8. The adapted HCB removes the Kirin display-engine device
and is staged at `overrides/chip_prod/etc/hdfconfig/hdf_default.hcb`.
An unrestricted hdf_devmgr and other donor hardware hosts remain excluded.

This component is **not enabled by build_stage2.sh**. The builder still uses
the eight-service native framework profile. Before enabling graphics,
stage2 needs matching module startup, read-only firmware/HDF binds and
selected character-device exposure inside its private /dev. It must retain
RAM-only writable storage and the physical block-device exclusion. Service
readiness, native-window/dma-buf interoperability, account activation and
SceneBoard installation/launch remain unresolved. No full image or DSU ZIP
is generated by these component and rendering tests.
